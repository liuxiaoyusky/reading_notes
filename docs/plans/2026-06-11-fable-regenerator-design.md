# 科目二寓言故事批量重生成设计

## 背景

现有 163 个 fable 文件中，约 80% 质量不达标。核心问题：
- 批量 loop 处理导致模型疲劳，走模板化捷径
- 后面的章节（第3章及以后）概念更抽象，AI 更难找到生动的类比
- 部分文件使用了条目式结构（"第一个角色...第二个角色..."），缺乏叙事性

## 目标

全部 163 个 fable 重新生成，统一为**连续叙事风格**——每个 fable 是一个完整的故事（有开头、人物对话、情节发展、结局），概念自然融入叙事中。

## 设计原则

1. **干净上下文**：每个 subagent 只收到它需要的源文件 + 风格指南 + 范例，不传递任何已生成内容
2. **并行处理**：用 Workflow 并行 spawn subagent，避免串行疲劳
3. **统一风格**：全部参照《老陈的陶罐》的连续叙事格式，禁止条目式结构
4. **质量自检**：每个 subagent 输出前自我检查
5. **人工抽检**：每章完成后抽检，不合格重跑

## 架构

```
┌─────────────────────────────────────────────────────────┐
│                    Fable Regenerator                      │
│                    (Workflow Script)                      │
├─────────────────────────────────────────────────────────┤
│  1. Scan: 遍历所有源 markdown 文件，生成任务列表          │
│  2. Batch: 按章节分批，每批并行处理                       │
│  3. Parallel Subagents: 每个 subagent 处理 1 个文件       │
│     ├── 输入: 源 markdown + 风格指南 + 3 个范例          │
│     ├── 处理: 按统一格式生成寓言故事                     │
│     └── 输出: 写好 fable 的 .md 文件                      │
│  4. Review (抽检): 每章完成后随机抽 2-3 个检查质量        │
│  5. 不合格 → 重跑；合格 → 下一章                         │
└─────────────────────────────────────────────────────────┘
```

## Subagent 输入规范

### 风格指南

你是金融寓言故事作家。你的任务是把枯燥的金融教材概念，变成生动的、有情节的寓言故事，帮助考生通过故事记忆概念。

【硬性规则——违反任意一条即为不合格】

1. **一个完整的故事**：必须有开头、发展、高潮、结局的完整叙事弧线。禁止条目式结构（如"第一个角色...第二个角色..."、"### 第一点...第二点..."）。

2. **必须有具体人物**：人物要有名字或具体身份，有对话和互动。
   - ✓ 好："村民阿福说：'老周，我这十两银子...'"
   - ✗ 差："投资者将资金交给管理人..."

3. **概念融入情节**：概念必须自然融入故事事件中，读者看完故事就懂了。不能在故事讲完后再贴概念解释。
   - ✓ 好：老周贴告示谁都可以加入 → 自然引出公募基金的概念
   - ✗ 差：先讲"公募基金是公开募集的"，再补一句"就像老周贴告示一样"

4. **叙事优先**：故事占全文 60% 以上。先有故事，后有原文定义和对应点表格。

5. **故事长度**：600-1200 字。太短讲不清，太长记不住。

6. **数学/公式类概念**：用生活场景中的具体事件来演示。比如用"分粮食"解释期望值，用"打赌"解释期权。

### 三范例（连续叙事风格）

每个 subagent 收到以下三篇范例的完整内容：

| 范例 | 故事名 | 概念类型 | 叙事特点 |
|------|--------|---------|---------|
| 范例1 | 《老陈的陶罐》 | 定义/起源 | 村民凑钱、老周统一管理、公开/非公开募集 |
| 范例2 | 《种果树的老农》 | 特点/分类 | 老农专种果树、长期收获、风险与收益 |
| 范例3 | 《按菜谱做菜的学徒》 | 机制/对比 | 学徒严格按菜谱、透明分散便宜 |

这三篇的共同特征：
- 一个完整的故事从头讲到尾
- 有人物对话和互动
- 概念随着情节推进自然呈现
- 没有分条目的小标题

## 输出格式

```markdown
# <原节标题>

## <emoji> 寓言故事 —— 《<故事名>》

<完整的故事，600-1200字，连续叙事，禁止条目式结构>

---

**📖 原文定义**

> 直接引用教材原文的定义，保持完整，不删减

> 可以多段引用

**💡 对应点**

| 故事元素 | 概念对应 |
|---------|---------|
| 故事中的具体事物/事件 | 教材中的专业术语 |
| ... | ... |

---

> 📝 来源：科目二 · 第X章第X节 · <标题>
```

### 格式规则

- 故事标题格式：`## <emoji> 寓言故事 —— 《<4-6字故事名>》`
- emoji 选择：🏺（通用）、🎯（特点/优势）、🔍（分析/方法）、📜（规则/制度）、⚖️（平衡/对比）
- 故事名要求：有画面感，4-6个字

## 分批策略

- 按 **章节** 分批，每章一次 Workflow 调用
- 同章概念有关联，subagent 可感知上下文一致性
- 每章内文件并行处理（受并发限制约 10-15 个同时跑）

## 质量检查（两阶）

### 第一阶：Self-Check（每个 subagent 自检）

输出前必须回答：
- [ ] 是否是一个完整的故事（开头→发展→高潮→结局），没有条目式结构？
- [ ] 是否有具体人物（有名有姓/有身份），有对话和互动？
- [ ] 概念是否自然融入情节中，而非故事后贴概念？
- [ ] 故事是否占全文 60% 以上？
- [ ] 故事长度是否在 600-1200 字之间？

### 第二阶：抽检（每章完成后）

- 随机抽取该章 20% 的 fable（最少 2 个）
- 检查标准：是否有故事？有人物对话？有情节？概念融入叙事？
- 不合格率 > 30% → 整章重跑
- 不合格率 ≤ 30% → 仅重跑不合格的

## 文件路径映射

```
源文件：converted/sections/<章>/<节>.md
    ↓
输出文件：converted/fables/<章>/<节>/<序号>-<标题>.md
```

如果一节 markdown 中有多个一级/二级标题，每个标题生成一个独立的 fable 文件。

## 进度追踪

- 每完成一章，更新 `batch-task.md` 中的进度
- 记录已完成的章节和文件数
- 记录失败的文件和重试状态

## 异常处理

- **subagent 超时/失败**：自动重试 1 次，仍失败则记录到错误列表，不阻塞其他任务
- **输出文件写入失败**：记录错误，人工处理
- **抽检不合格**：标记该批次为需重跑，重新 spawn subagent

## 重生成范围

全部 18 章、约 163 个 fable 文件全部重新生成。不保留任何现有文件（设计文档完成后会先备份）。
