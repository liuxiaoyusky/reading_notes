# 寓言大改润色 v3 — Master Prompt（Subagent 1 改写 + Subagent 2 验收 + 循环改进）

## 整体流程

```
┌─────────────────────────────────────────────────────────────┐
│ Master Prompt v3 (本文档)                                   │
│   包含 改写规则 + 验收规则 + 失败反馈循环                    │
└─────────────────────────────────────────────────────────────┘
        ↓                                  ↑
   Subagent 1                            Subagent 2
   (改写 worker)                         (验收 reviewer)
        ↓                                  ↓
   写改后 .md                    评估每篇档位（A/B/C）
   写 _human_touch_log.md        不合格 → 把具体失败点反馈
        ↓                           ↓
        └────────→ 通过 ←────────────┘
                  ↓
            标记 "verified_A"
```

## Subagent 1（改写 worker）规则

### 默认档位：**A 大改**（禁止默认 B 小调、禁止 SKIP）

- 每篇必须 A 大改——重写故事结构、加人物对话、加场景动作、加心理转折
- 只有**极少数特殊情况**才允许 B 或 SKIP，且必须详细记录理由

### 什么是 A 大改（必做清单）

1. **重塑结构**：原文若是 PPT 式"第一种/第二种/第三种"分点，改成连贯叙事（一个人物提问 / 一个人物回答 / 一个人物反问）
2. **加人物对话**：每篇至少 3-5 处具体对话，包含 1 处反问、1 处沉默、1 处自我修正
3. **加场景动作**：每篇至少 3 处具体动作（"把茶碗往桌上一顿"、"烟杆换了三回"、"袖上还沾着晨雾的水汽"）
4. **加心理停顿**：每篇至少 2 处人物犹豫、内心矛盾、未说完的话
5. **重写收尾**：原文若是金句式总结（"XX 的本质是 YY"），改成具体场景收尾（"从此以后那只匣子成了他铺子里的定心丸"）
6. **场景感升级**：把抽象概念具象化（"衡量业绩的尺子" → "小顾先生提着箱子登场、箱子里齐齐整整五把秤"）

### 什么情况可以 B 小调（**严禁滥用**，且需在 log 里详细说明）

- 原作已经有大量具体对话、人物、场景推进——但这种情况很少
- 如果选了 B，必须在 log 里写："原文已含 ≥5 处对话、≥3 处动作、≥2 处心理停顿——证据：贴出原文片段"

### 什么情况可以 SKIP（**几乎不允许**）

- 文件结构损坏（如 17 章 04-基金清算报告那种缺原文定义段）——按规则跳过
- 文件非寓言格式（如 progress.md、README.md）——跳过
- 其他情况**都不允许 SKIP**

### 硬约束（绝对不能违反）

#### 1. 只动故事段，其他不动

```
# 章节标题             ← 不动
## 🏺 寓言故事 —— 《XXX》   ← 不动《XXX》那个书名号
[故事段]              ← 改这里
---
**📖 原文定义**        ← 不动
[定义段]              ← 不动
**💡 对应点**          ← 不动
[表格]                ← 不动
> 📝 来源             ← 不动
```

#### 2. 保留所有核心元素

- 人物名字（老陈、老周、顾先生、贾先生、老冯 等）
- 机构名（穆迪 Moody's、S&P、惠誉 Fitch、深交所、上交所 等）
- 核心数字（年息七厘二、面值一百两、BBB-、AUM、CAPM、VaR、波动率 等）
- 年代（一九五二年、清乾隆四十一年 等）
- 地名（十六铺码头、米行 等）

**改写后必须** 对照 `**💡 对应点**` 表格逐条检查：表格里每个故事元素在改后故事里**必须还在**。如果新结构丢了一个概念，补回去。

#### 3. 不允许的 AI 痕迹（绝对禁止）

- ❌ 三短句排比（"更智能、更高效、更人性化"）
- ❌ 四字成语堆砌（一段里 ≥2 个）
- ❌ 破折号 `——` 堆砌（一段里 ≥2 个）
- ❌ 翻译腔（"作为 XX"、"对 XX 进行 XX"、"不仅...而且..."）
- ❌ 金句式总结（"XX 的本质是 YY"、"归根结底 XX"）
- ❌ 同义词循环（同一个东西换着叫）
- ❌ 模板段落（"总之综上所述"）
- ❌ 每篇都出现的"自我修正"——这一招最多**全篇一次**
- ❌ 语气词堆砌（吧/嘛/呗/啊/哦）—— 整篇最多 1-2 个
- ❌ 新增 `##` 小标题或 emoji-led 段头

#### 4. 强度上限（防止走偏）

- 整篇语气词 ≤2 个
- 整篇自我修正 ≤1 处
- 整篇破折号 `——` ≤2 个
- 整篇四字成语 ≤2 个
- 不堆排比（任何并列 ≥3 个短句就重写）

#### 5. 文件操作

- 用 **Read** 拿原文
- 用 **Write** 覆盖整个文件（不要 Edit，zsh 中文路径会 mismatch）
- Write 时保留原文定义段/对照点/来源行一字不动——**只能改故事段**
- 改完一篇，写日志到 `<chapter_path>/_human_touch_log.md`

### 工作流

```
1. Read <path>
2. 找到 📖 原文定义 段，列出每个 💡 对应点表格里的故事元素
3. 重写故事段（A 大改）：
   - 用具体人物对话代替 PPT 式罗列
   - 加场景动作、心理停顿、自我修正（≤1）
   - 重写收尾为具体场景而非金句
4. Write <path> 改后内容（保留非故事段一字不动）
5. 验证：对照原文 💡 对应点表格，确认每个元素在改后故事里**还在**
6. 写到 _human_touch_log.md：
   - 档位：A
   - 改动摘要：一句话
   - 验证：✓ / ✗（对照点保留情况）
```

## Subagent 2（验收 reviewer）规则

### 任务

拿到 Subagent 1 改完的 .md 文件和 _human_touch_log.md，**逐篇验收**。

### 验收标准（每篇都要过）

#### 必须通过（A 大改才算合格）

1. **结构变化**：故事段的句子数 / 行数相对 HEAD 增长 ≥ 50%
   - 例：原文 500 行的故事段，改后必须 ≥ 750 行
   - 例外：原文本身已有 ≥1000 行（极少见）——这种按 B 标准验
2. **对话密度**：每篇至少有 3 处明确的对话（含引号或破折号引导的对话）
3. **场景动作**：每篇至少 3 处具体动作描写（不是抽象"考虑"、"思考"，是"把茶碗往桌上一顿"、"烟杆换了三回"这种）
4. **心理停顿**：每篇至少 1 处人物犹豫 / 沉默 / 未说完的话
5. **收尾非金句**：最后一段不是"XX 的本质是 YY" / "XX 的根本是 YY" / "总之 XX" 形式；最好是具体场景收尾
6. **对照点保留**：💡 对照点表格里的所有故事元素在改后故事里**全部出现**
7. **核心数字/术语/机构名/人名**：与 HEAD 完全一致（不允许改动）
8. **原文定义/对照点/来源行**：与 HEAD 完全一致（一字不动）

#### 不可触发（任何一条命中就 FAIL）

- 整篇语气词 >3 个
- 整篇四字成语 >3 个
- 整篇破折号 >3 个
- 三短句排比（连续三个以上短句并列）
- 故事元素→概念对应缺失
- 数字/术语/机构名/人名被改动

### 验收产出

每个文件写一条 verdict：

```
## <相对路径/文件名>
- verdict: PASS / FAIL
- 档位: A（实际）/ B（实际）
- 行数对比: HEAD=500  改后=750  增长=50%
- 对话数: 5 处（≥3 通过）
- 动作数: 4 处（≥3 通过）
- 心理停顿: 1 处（≥1 通过）
- 收尾形式: 具体场景（通过）
- 对照点保留: ✓ 全部 8 个元素
- 核心数字/术语/人名: ✓ 未改
- 不可触发项: 全部未命中
- 失败点（FAIL 时填）：
  - 行数不足：原 500 改后 480（-4%，未达 50%）
  - 收尾金句：最后一段是"XX 的本质是 YY"
  - ...
- 建议修复方向（FAIL 时填）：
  - 加一节具体对话场景
  - 把金句改写为场景
  - ...
```

### 输出文件

写到 `<chapter_path>/_review_log.md`，**不要修改 .md 文件或 Subagent 1 的 log**。

## Master 修改 Prompt 的时机

每次 Subagent 2 验收完一章，把 `_review_log.md` 看一遍：

### 情况 A：通过率 ≥ 80%

- Prompt 不改，继续
- 这一章标 "verified"，可以进入下一章

### 情况 B：通过率 < 80%

- 找失败原因：**是 worker 没遵守规则，还是规则本身不清楚？**
- 修改 master prompt 增加明确指令：
  - 例：如果 worker 普遍漏掉"心理停顿" → 在硬约束里加红色警告"心理停顿 ≤1 是上限，不是目标"
  - 例：如果 worker 普遍保留金句收尾 → 加"金句收尾 = FAIL"的红线
- 修改后，**只跑未通过的几篇**，不重跑整章（节省 token）
- 重新走 Subagent 1 → Subagent 2 循环

## 启动流程

每次启动一组（4-6 worker 并发）：

```
1. 主会话启动 N 个 Subagent 1（每个 worker 处理一章），背景任务
2. 等所有 Subagent 1 完成
3. 主会话启动 N 个 Subagent 2（验证 worker，每个对应一章），背景任务
4. 等所有 Subagent 2 完成
5. 主会话读 _review_log.md，统计通过率
6. 通过率 ≥80% → 进入下一组（章节未改的）
6. 通过率 <80% → 修改 prompt，循环补完本章
7. 全部章节 verified → commit
```
